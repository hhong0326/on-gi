# 0014. 기도 쓰기·피드는 RPC로만, 기도 시간은 서버가 상한

- 상태: 채택
- 날짜: 2026-11-13

## 배경
`prayers`를 클라이언트가 직접 읽고 썼다. 그래서
- 누구나(익명 포함) 모든 기도의 `user_id`·`church_id`·기도 시간을 읽을 수 있어, 다른 교회 누적 시간을 합산할 수 있었고(0010 위반) 특정 사용자의 날짜별 위치를 이어 붙일 수 있었다(0004 취지 위반)
- 자기 기도 행의 `church_id`·`duration_seconds`를 임의로 써서 아무 교회나 즉시 최고 단계로 올리고 이웃 온기까지 퍼뜨릴 수 있었다
- 폴링이 `prayed_at` 기준이라 남의 기도가 끝나거나 재시작돼도 화면에 반영되지 않았다

## 결정
- 지구본 피드는 `get_prayer_feed` RPC로만: 위치·시각·`is_active`·`is_mine`만 돌려준다. 폴링 기준은 새 컬럼 `updated_at`
- 기도 시작은 `start_prayer`: 0.1도 격자 반올림과 사용자 시간대 기준 하루 1행을 서버가 지킨다. 같은 날 이전 시간은 `prior_seconds`에 보존
- 기도 마치기는 `end_prayer`: 이번 시간 = `min(클라이언트 측정, 서버 경과, app_config.prayer_limits.maxSessionSeconds)`. 이미 마친 기도면 저장값을 돌려준다(재시도 안전)
- 통계는 본인 것만(`get_my_prayer_stats`). 남의 통계를 볼 수 있던 `get_prayer_stats(p_user_id, ...)`는 삭제
- 직접 접근 차단: `prayers`는 본인 행 읽기만, `churches`는 직접 읽기 불가(초대 코드·만든 사람 비공개), `users`는 닉네임만 직접 수정

## 이유
원칙(0004, 0010)을 클라이언트 코드가 아니라 DB 권한으로 지킨다. 클라이언트 측정값을 함께 받는 이유는 저장 실패 후 재시도할 때 서버 경과만 쓰면 그 사이 시간까지 기도로 잡히기 때문이다. 서버 경과가 상한이라 실제 흐른 시간보다 부풀릴 수 없다.

## 영향 · 후속
- 배포는 두 단계: `prayer_rpc`(추가만, 옛 클라이언트 호환) 적용 → 새 클라이언트 배포 → `supabase/pending/`의 `prayer_lockdown`을 migrations로 옮겨 적용. 한 번에 하면 옛 탭에서 기도 시작/마치기가 실패한다
- 남은 한계: 익명 계정을 많이 만들어 실제 시간을 들여 기도를 켜두면 시간을 쌓을 수 있다. 계정당 하루 상한, 익명 가입 제한(CAPTCHA)은 후속 과제
- 진행 중인 기도(`duration_seconds` null)는 통계·교회 누적에서 빠진다 (기존과 같음)
