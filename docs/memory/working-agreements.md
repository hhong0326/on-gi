# 작업 방식

> 이 프로젝트에서 사람과 AI 에이전트가 함께 지키는 규칙. 각 규칙은 실제로 문제가 됐던 경험에서 나왔다.

## 진행 순서: 논의 → 합의 → 구현

작은 수정이 아니면 코드를 바꾸기 전에 (1) 원인·현상 분석 공유 → (2) 접근 방식 제안 → (3) 확인 → (4) 구현 순서로 한다.
**이유:** 방향을 함께 정하고 싶고, 바로 구현하면 의도와 다른 쪽으로 가기 쉽다.

## 확인 없이 하지 않는 것

- DB 마이그레이션 **실행** (로컬·운영 모두. SQL 작성은 먼저 해서 보여준다)
- 의존성 설치
- 운영 데이터 변경, 배포

## 커밋 전에 화면으로 확인

변경 후 → `npm run build` → Playwright로 화면 테스트·스크린샷 → 확인 → 커밋.
**이유:** 빌드 성공만으로는 실제 렌더링 문제를 놓친다.

- **모바일 뷰포트(390×844 등)는 반드시** 확인한다. 하단 UI(탭바, 드롭다운, 시트)가 특히 잘 잘린다
- 재검증 전에 서버가 **새 빌드를 서빙하는지** 확인한다: 포트 기준으로 프로세스 종료(`lsof -ti :PORT | xargs kill`) → 서빙 청크에서 새 코드 패턴 grep

## 하지 않는 것

- 초대코드 입력 UI를 다시 넣지 않는다 ([0002](../decisions/0002-remove-invite-code-input.md))
- RLS 정책 없이 테이블을 만들지 않는다
- `src/lib/supabase/` 설정 파일을 임의로 바꾸지 않는다
- 지도 렌더링 루프(애니메이션)에 React 상태를 넣지 않는다 — Mapbox paint 속성만 갱신
- WebSocket을 쓰지 않는다 (polling 방식)

## 옮길 때 빠뜨리지 않기

metadata나 설정을 다른 파일로 옮길 때는 원본의 **모든 필드**를 diff로 대조한다.
**이유:** i18n 리팩토링에서 번역 필드만 옮기다 manifest·icons가 빠져 PWA standalone 모드가 깨졌다.

## 결정과 기억 남기기

- 방향을 정한 결정 → [docs/decisions/](../decisions/)에 ADR 추가
- 작업을 마치면 → [project-state.md](project-state.md)의 기능·함정·백로그 갱신
- 저장소가 공개이므로 개인 정보, 키, 비밀번호는 어디에도 적지 않는다
